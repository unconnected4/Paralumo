# Backend: intent

Scope: the multi-user JSON API behind every client. It covers auth, dictionary lookup via providers, the user's vocabulary (cards), SRS scheduling and review logging, and later the game endpoints. Product context: [../intent.md](../intent.md). Detailed data model and endpoints: [../docs/plan.md](../docs/plan.md).

## Stack
- **Java 25** (LTS), **Spring Boot 4** (Spring MVC), **Spring Data JPA** (Hibernate), **Flyway**, **Postgres 16**
- **Gradle** with the Kotlin DSL and the wrapper; versions in `gradle/libs.versions.toml`
- Spotless (google-java-format) for formatting; Error Prone + NullAway with JSpecify annotations for static checks and null safety; JUnit Jupiter, AssertJ and MockMvc for tests
- Auth via **Spring Security** (email + password), so we don't write the security machinery ourselves
- OpenAPI spec generated by **springdoc-openapi**
- SRS: FSRS, wrapped in `service/SrsService`. Library choice is open (see Open questions)

## Decisions
- **Backend in Java (by Alex):** "backend is going to be implemented in Java." Alex chose Spring Boot over Quarkus and Micronaut, Gradle (Kotlin DSL) over Maven, and Spring Data JPA + Flyway over jOOQ and Spring Data JDBC (2026-10-26). This replaces the earlier FastAPI plan; nothing had been scaffolded, so no code is migrated.
- **Saved cards copy the sense data**, so they stay intact if the dictionary source changes or drops a sense.
- **Every review is logged** (`review_logs`, with `source = 'srs' | 'match_game'`) so the algorithm can change without losing history.
- **Dictionary sources sit behind `DictionaryProvider`.** Implementations: `fake` (hand-authored data in our own shape, for dev/test/CI) now, and `yandex` as the first live provider later, with more to follow.
- **Plain JSON API only.** No server-rendered HTML, so Android can reuse it unchanged. The spec is generated by springdoc from the controllers and DTOs and exported with `./gradlew exportOpenApi` to `docs/api/openapi.json`; it is never hand-edited.
- **JSON shape matches the Step 0 contract:** snake_case field names (`sense_id`) through a global Jackson naming strategy, and errors as RFC 9457 `ProblemDetail`, whose `detail` field is the `{detail}` the web client reads. Validation errors map to `422`, as the contract expects, not Spring's default `400`.
- **Layering:** `api/` (thin controllers) → `service/` (logic) → `persistence/` + `provider/`. Controllers never talk to providers or repositories directly.
- **Segregated implementations (by Alex):** see root [intent.md](../intent.md). Every fake or mocked part of the backend (the `fake` dictionary provider, and any in-memory stand-in used before Postgres exists) is its own implementation of an interface, in its own package, and is selected by configuration (a conditional bean on `DICTIONARY_PROVIDER`) or test setup. Services and controllers never branch on whether they run against a fake. Replacing a fake with the real implementation must not change the code that uses it.
- **Auth transport:** one signed JWT (`AUTH_SECRET`), accepted from two places: an httpOnly, SameSite=Lax cookie for the web SPA (same-origin behind the Vite proxy, no JS token storage) and an `Authorization: Bearer` header for future mobile/Android clients. Auth endpoints are our own JSON controllers over Spring Security's `AuthenticationManager` and `PasswordEncoder`, because Spring's form-login defaults (form fields, redirects) don't match the Step 0 contract. CSRF handling for the cookie is settled in Step 1.
- **Card retention:** `user_cards` uses soft deletion (`deleted_at TIMESTAMP NULL`). Re-saving a deleted card restores it (`deleted_at = NULL`), keeping its copied sense data, notes, custom examples, and FSRS state intact. A single unique constraint on `(user_id, sense_id)` applies. Active card filtering (`deleted_at IS NULL`) is centralized in `service/CardService`.
- **Public sense identification:** The API's `sense_id` is an opaque deterministic string owned by the backend (e.g. a hash of provider + lemma + pos + main translation). Clients never parse it. Any provider, including `fake`, computes it statelessly without a database, ensuring deterministic IDs across resets. In Step 1, Postgres stores this as `senses.source_key` and `user_cards` resolves it.
- **Backend implementation follows Web UI (by Alex):** "we are implementing web ui now. Based on them we will implement backend." Backend scaffolding and implementation are deferred until the Web UI is built and its UX and data needs are proven in practice. The backend schemas, endpoints, and data model will be designed and implemented to satisfy that proven contract.
- **Fake data location:** Fake provider data is hand-authored in our own domain shape and lives in `src/main/resources/fake-data/<word>.json`, because the fake provider is runtime code (used in local development and Docker builds). Raw provider responses for Yandex belong to the later integration step.
- **Migrations are forward-only.** Flyway Community has no undo, so a bad migration is fixed by a new one. Combined with backward-compatible migrations (expand → migrate → contract), the previous release keeps working against the new schema.
- **Port 8000**, so the web dev proxy (`API_PROXY_TARGET`, default http://localhost:8000) works unchanged.
